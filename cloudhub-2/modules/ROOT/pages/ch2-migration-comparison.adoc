[%collapsible]
====
// NOTE: This subsection is new content called for by the improvement plan (Section 1.1 item 1
// and Section 2.1). Content below is drawn from the existing comparison tables and expanded
// with feature mapping. Verify routing capabilities and URL rewrite equivalents with engineering.
// This section is NOT shared via include — it is migration-specific context.

When migrating from a Dedicated Load Balancer (DLB) to CloudHub 2.0's ingress load balancer, review this feature mapping:

[cols="1,1,1"]
|===
|Feature |CloudHub DLB |CloudHub 2.0 Ingress

|SSL/TLS termination
|SSL termination happens at the DLB layer.
|SSL termination happens at the ingress load balancer layer.

|Certificate management
|Upload PEM-encoded certificates and private keys manually. Limited CA certificate support.
|Default TLS context with wildcard certificates created automatically. Custom vanity domains supported with your own TLS context. Dynamic certificate management with in-place updates without redeployment.

|URL rewriting
|Configured at the DLB level using mapping rules.
|Configured at the application level using domains and endpoints for per-app configuration.

|Mutual TLS (mTLS)
|DLB handles mTLS at the infrastructure level, performing client certificate validation and forwarding certificate information to applications via HTTP headers. Supports an *optional* mode that performs client certificate validation but still passes the request through if the check fails. Accepts certificate files in PEM format only.
|Native mTLS with TLS contexts and truststores. Configure mTLS at the private space level with centralized management. Supports forward SSL. Upload truststore files in PEM and JKS formats. Optional mTLS mode is not supported — client certificate validation either passes or the request is rejected.

|Protocols
|HTTP, HTTPS, TCP, WebSockets (ws and wss)
|HTTP, HTTPS, TCP. TCP traffic is supported only on newly created private spaces. Upgraded private spaces do not support TCP traffic. If you require TCP, create a new private space.

|Logging
|No DLB log support.
|Download ingress traffic logs from Runtime Manager.

|High availability
|Up to four load balancer units (up to eight workers total).
|Auto-scales to accommodate traffic. Replicas are automatically distributed across two or more availability zones (AZs).
|===


[discrete]
==== Routing Capabilities Comparison

DLB uses *mapping rules* to route requests. CloudHub 2.0 uses *endpoint and path configuration* per application. This table maps the DLB routing model to the CloudHub 2.0 equivalent:

[cols="1,2,2"]
|===
|Routing Capability |CloudHub DLB (Mapping Rules) |CloudHub 2.0 (Endpoints & Paths)

|Path-based routing
|Mapping rules define an *Input Path* (supports patterns with `{variables}`), a *Target App*, and an *Output Path* (literal only). The first matching rule wins (priority-ordered). Example: `/api/v1/` → `my-app` with output `/`.
|Each application configures its own endpoints with a *Path* (where clients reach the app) and a *Path Rewrite* (the base path the HTTP Listener expects). Configured per-app in the *Ingress* tab. No global priority ordering needed — each app owns its endpoint.

|Host-based routing
|DLB uses certificate endpoints (CN or SANs) to match hosts. A wildcard certificate (`*.example.com`) combined with a `{subdomain}` variable in the mapping rule routes `api.example.com` to the `api` app.
|CloudHub 2.0 uses *Domains* configured via TLS contexts at the private space level. Each app selects its domain from a dropdown and specifies a subdomain. Supports the `app-name` placeholder to auto-resolve. Multiple endpoints per app are supported.

|URL rewriting
|Configured at DLB level. Input Path defines the client-facing path; Output Path defines what is passed to the app. Patterns only in Input Path; Output Path is always literal.
|Configured at app level via *Path* and *Path Rewrite* fields. Path is the client-facing URL; Path Rewrite is the internal path for the HTTP Listener.

|Multi-app routing on one domain
|Single DLB can route to multiple apps via ordered mapping rules on the same SSL endpoint. Pattern variables (`{app}`, `{layera}`, `{domaina}`) enable dynamic routing.
|Each app registers its own endpoint(s) on shared domains. No global rule list — each app's endpoint is independent. Use unique paths or subdomains to differentiate.

|Protocol selection
|Mapping rules specify upstream protocol per rule: `http` (port 8091), `https` (port 8092), `ws` (8091), `wss` (8092).
|CloudHub 2.0 apps listen on port 8081 for both HTTP and HTTPS. Protocol is determined by TLS context configuration, not per-rule. WebSocket support via HTTP/HTTPS endpoints.

|Wildcard matching
|Pattern variables (`{variable}`) in Input Path match `a-z0-9.&?-_` (no slashes). Priority order controls which rule matches.
|Subdomain placeholders (`app-name`, `business-group-id`, `environment-id`) provide dynamic matching. No regex or custom variable patterns.
|===

*Migration considerations:*

* DLB mapping rules are *centralized* (one ordered list per SSL endpoint). CloudHub 2.0 endpoints are *distributed* (each app manages its own routing). This removes priority conflicts but requires each app to have unique endpoint definitions.
* DLB's flexible regex-like patterns (`{variable}`) don't have a direct equivalent in CloudHub 2.0. Apps that rely on dynamic path-to-app-name routing must be reconfigured with explicit per-app endpoints.
* CloudHub 2.0 Path Rewrite supports static per-app mappings, addressing the DLB Output Path limitation that patterns aren't supported.
* CloudHub 2.0 supports ingress URIs up to 4 KB. Before migrating, identify clients that send request paths or query strings larger than 4 KB and redesign those requests. See xref:ch2-limits.adoc[Limits in CloudHub 2.0].

For full DLB mapping rules reference, see https://docs.mulesoft.com/cloudhub/lb-mapping-rules[Dedicated Load Balancer Mapping Rules]. +
For CloudHub 2.0 endpoint configuration, see https://docs.mulesoft.com/cloudhub-2/ch2-config-endpoints-paths[Configuring Endpoints and Paths for Apps Deployed to a Private Space].


[discrete]
==== Certificate Migration

The VPC upgrade tool migrates DLB configurations to the new private space on a best-effort basis only. Due to architectural differences between the CloudHub 1.0 DLB and the CloudHub 2.0 ingress controller, automated migration of certificates and vanity domains isn't guaranteed.

IMPORTANT: Applying certificate changes in the CloudHub 2.0 private space doesn't impact your live CloudHub 1.0 environment. The two environments are isolated; your existing DLB continues to handle traffic normally until you manually update your DNS CNAME records to point to the new ingress endpoint.

To manually migrate DLB certificates to your CloudHub 2.0 private space:

. *Inventory your DLB certificates:*
** In *Runtime Manager*, navigate to *CloudHub* > *Load Balancers*.
** Record all certificates, vanity domains, and Subject Alternative Names (SANs).

. *Identify incompatible TLS ciphers:*
+
CloudHub 2.0 doesn't support TLS 1.1 ciphers. You can't migrate the following ciphers:
+
* `ECDHE-ECDSA-AES128-SHA1`
* `ECDHE-ECDSA-AES256-SHA1`
* `ECDHE-RSA-AES128-SHA1`
* `ECDHE-RSA-AES256-SHA1`
+
If your DLB uses any of these ciphers, reissue certificates with TLS 1.2+ compatible ciphers before migrating.

. *Upload certificates to the private space:*
** In *Runtime Manager*, navigate to your private space and select the *Domains & TLS* tab.
** Manually upload your server certificates and private keys.
+
NOTE: DLB requires a full certificate chain that includes intermediate and root certificates in a single file. For the CloudHub 2.0 private space, split intermediate and root certificates into a separate file and upload it as the *CA Path Certificate*.

. *Verify SANs:*
** Confirm that all Subject Alternative Names for your vanity domains are correctly listed in the uploaded certificate.

. *Create TLS contexts:*
** Create a TLS context for each vanity domain or group of domains that share a certificate.
** Verify that the TLS context is active before switching traffic.

For more information, see https://help.salesforce.com/s/articleView?id=005237268&type=1[Missing DLB Certificates During CloudHub 1.0 to CloudHub 2.0 Migration (KA 005237268)].


[discrete]
==== Allowlist and Denylist Migration

When migrating from a DLB to CloudHub 2.0 ingress, your allowlist rules translate to private space firewall rules. CloudHub 2.0 firewall rules are allow-only — there's no deny rule equivalent.

[cols="1,1"]
|===
|CloudHub DLB |CloudHub 2.0 Private Space

|DLB allowlist (IP addresses/CIDRs permitted to reach DLB)
|Ingress firewall rules on the private space

|DLB denylist (blocked IPs)
|No deny rule equivalent. Allow only the CIDRs you need, or block upstream with a WAF or Flex Gateway policy.
|===

To migrate access control rules:

. *Export current DLB allowlist:*
** Record all CIDR ranges configured on your DLB allowlist.

. *Create firewall rules in the private space:*
** In *Runtime Manager*, navigate to *Private Spaces* > *[your space]* > *Firewall Rules*.
** Add ingress rules for each CIDR range that was in your DLB allowlist.
** See xref:ps-config-fw-rules.adoc[Configure Firewall Rules for a Private Space].

. *Add infrastructure CIDR ranges:*
+
If your CloudHub 2.0 applications need to communicate with applications still on CloudHub 1.0, add the following CIDR ranges to the DLB allowlist:
+
* `100.64.0.0/16`
* `100.66.0.0/16`
* `100.67.0.0/16`
* `100.68.0.0/16`
+
These ranges enable cross-platform communication during phased migration.

[discrete]
==== Network Topology

.Hybrid Migration State
[cols="1,2,2",options="header"]
|===
|Layer |CloudHub 1.0 VPC |CloudHub 2.0 Private Space

|Internet ingress
|External clients send HTTPS traffic on port 443 to the Dedicated Load Balancer (DLB).
|External clients send HTTPS traffic on port 443 to the ingress load balancer.

|Load balancing and routing
|The DLB terminates TLS and applies ordered mapping rules.
|The ingress load balancer terminates TLS and routes requests by domain and path.

|Application runtime
|Workers receive HTTP or HTTPS traffic on ports 8091 and 8092.
|Replicas receive traffic on port 8081.

|Connectivity during migration
|Workers accept inbound calls from CloudHub 2.0 over the `100.64.0.0/16`, `100.66.0.0/16`, `100.67.0.0/16`, and `100.68.0.0/16` ranges, provided those ranges are added to the DLB allowlist.
|Replicas can call CloudHub 1.0 workers through the DLB using those same ranges, and connect to on-premises or AWS systems through the Transit Gateway using the private space CIDR.

|Outbound traffic
|Workers reach backend systems through the VPC network and Transit Gateway.
|Replicas use the NAT Gateway when backend systems require outbound static IP addresses.

|Backend connectivity
2+|Both environments connect to backend systems, such as databases and SaaS APIs, through the Transit Gateway.
|===

.Traffic Paths During Hybrid Migration
* *CloudHub 1.0 path:* External client -> DLB -> CloudHub worker -> Transit Gateway -> backend system.
* *CloudHub 2.0 path:* External client -> ingress load balancer -> CloudHub 2.0 replica -> Transit Gateway or NAT Gateway -> backend system.
* *Cross-platform path:* A CloudHub 2.0 replica can call a CloudHub 1.0 worker through the DLB, provided the `100.64.0.0/16`, `100.66.0.0/16`, `100.67.0.0/16`, and `100.68.0.0/16` ranges are added to the DLB allowlist. These ranges aren't for CloudHub 1.0 reaching CloudHub 2.0, and a private space can't use them as its own CIDR.

.Traffic Flow: DLB and Ingress Controller
[cols="1,2,2",options="header"]
|===
|Stage |CloudHub 1.0 Path |CloudHub 2.0 Path

|DNS resolution
|The client requests `myapp.example.com`, which resolves to `[lb-name].lb.anypointdns.net`.
|The client requests `myapp.example.com`, which resolves to `[space-id].[region].cloudhub.io`.

|TLS and routing
|The DLB terminates TLS and evaluates its mapping rules.
|The ingress load balancer terminates TLS and matches the configured domain and path.

|Application request
|The DLB sends HTTP traffic to the CloudHub worker on port 8091.
|The ingress load balancer sends HTTP traffic to the CloudHub 2.0 replica on port 8081.
|===

.Traffic Switching During Migration
CloudHub 2.0 provides two ways to cut over traffic. Choose one, don't mix them for the same application:

* *Gradual, DLB-managed switch:* Keep the DNS CNAME pointed at the DLB and use the traffic-switching API or UI to shift a percentage of traffic between the CloudHub 1.0 worker and the CloudHub 2.0 ingress load balancer, which then routes to the CloudHub 2.0 replica. The DLB and the CloudHub 2.0 private space it targets must support this split; see xref:ch2-migration-validate.adoc[Step 4: Validate and Switch Traffic].
* *Full DNS cutover:* Repoint the CNAME for `myapp.example.com` directly from the DLB to the CloudHub 2.0 ingress endpoint. The DLB and SLB can't route to applications in a migrated private space, so this is an all-or-nothing switch rather than a gradual one.

For step-by-step DLB migration guidance, see xref:ch2-migration-infrastructure.adoc[Step 2: Prepare Infrastructure].

[%collapsible]

When migrating from a DLB to CloudHub 2.0 ingress, the following operational behaviors change. These differences affect production traffic and can require changes to your applications.


[discrete]
==== HTTP Header Injection

The CloudHub DLB injects HTTP headers that your applications can depend on for routing, logging, or security decisions. CloudHub 2.0's ingress load balancer doesn't inject most of these headers by default.

*DLB-injected headers not available in CloudHub 2.0:*

[cols="1,2"]
|===
|Header |Purpose

|`x-ch1-path`
|Preserves the original request path before DLB mapping rules are applied.

|`X-Forwarded-Proto-Real`
|Original protocol (HTTP/HTTPS).
|===

*mTLS client-certificate headers:*

CloudHub 2.0's ingress doesn't inject `X-SSL-Client-*` headers by default. Enable *Forward SSL Session* in the TLS context to forward client certificate information to your application via these headers:

[cols="1,2"]
|===
|Header |Purpose

|`x-ssl-client-cert`
|The client certificate.

|`X-SSL-Client-Verify`
|Client certificate verification status (for mTLS).

|`X-SSL-Client-DN`
|Client certificate distinguished name.

|`X-SSL-Issuer`
|Client certificate issuer.

|`X-SSL-Client-Serial`
|Client certificate serial number.
|===

WARNING: These headers are appended to, not overridden on, incoming requests. A client that sets its own `X-SSL-Client-*` header before the ingress forwards the real value can spoof certificate data unless your application strips client-supplied values first.

*Headers forwarded by default:*

[cols="1,2"]
|===
|Header |Purpose

|`X-Real-IP`
|Original client IP address.

|`X-Forwarded-For`
|Forwarded client IP addresses. See https://help.salesforce.com/s/articleView?id=001123394&type=1[KB 001123394] for how CloudHub 2.0 populates this header.
|===

*DLB security response headers (injected on responses):*

* `Strict-Transport-Security: max-age=31536000; includeSubdomains;`
* `X-Content-Type-Options: nosniff`
* `X-Frame-Options: SAMEORIGIN`
* `X-XSS-Protection: 1; mode=block`

*Migration impact:*

* If your application reads `X-SSL-Client-*` headers for mTLS-based authorization decisions, enable Forward SSL Session in the TLS context, and strip any client-supplied values for these headers before trusting them.
* If your application relies on `x-ch1-path` for original path preservation, then note that CloudHub 2.0 doesn't apply global mapping rules — the application receives the request path directly as configured in its endpoint.
* If downstream security appliances or browsers depend on the DLB's injected security response headers (`HSTS`, `X-Frame-Options`, and others), then configure your Mule application to return these headers explicitly in responses.

For full reference, see https://docs.mulesoft.com/cloudhub/lb-reserved-headers[Dedicated Load Balancer Reserved Headers].


[discrete]
==== Connection Timeouts and Keep-Alive

Connection timeout behavior differs between CloudHub DLB and CloudHub 2.0 ingress:

[cols="1,2,2"]
|===
|Behavior |CloudHub DLB |CloudHub 2.0 Ingress

|Idle connection timeout
|300 seconds (default). If no data is sent or received within this duration, the DLB closes the connection.
|15 seconds (hardcoded, not configurable). For each request, the load balancer maintains two connections (client→LB and LB→app). If no data is sent or received on either connection within this duration, the load balancer closes both connections.

|Keep-alive timeout
|60 seconds. Connections are closed after new workers come online and the DNS TTL (30 seconds) expires.
|Not separately configurable. Governed by the idle connection timeout above.

|Read-request timeout
|Included in the 300-second idle timeout window.
|300 seconds (hardcoded, not configurable). The maximum time the ingress controller waits to receive the complete request from the client. Applies to both shared and private spaces.

|Read-response timeout
|Included in the 300-second idle timeout window.
|300 seconds by default. Configurable up to 3,600 seconds (1 hour) via *Read Response Timeout* in the *Advanced* tab of your private space settings. This is the time the ingress controller waits for a response from your Mule application.
|===

*Migration impact:*

* CloudHub 2.0 has a 15-second idle timeout, compared with the DLB's 300-second default, and it isn't configurable. This affects clients that use persistent connections (connection pools) with a client-side idle timeout higher than 15 seconds. For example, a client configured with a 60-second idle timeout works with the CH1 DLB (60s < 300s) but causes premature connection closures in CloudHub 2.0 (60s > 15s). Reduce the client-side idle timeout to a value below 15 seconds (for example, 10 seconds).
* The read-request timeout is hardcoded to 300 seconds and isn't configurable. If a client takes longer than 300 seconds to send the complete request payload (for example, uploading a large file), CloudHub 2.0 drops the connection even if you configure a longer read-response timeout. For data transfers that exceed 300 seconds, break the request into smaller chunks or use an asynchronous processing pattern.
* For long-running synchronous requests that expect a response, the *Read Response Timeout* applies, not the idle timeout. Customize this value, up to 3,600 seconds, in the *Advanced* tab of your private space settings in Runtime Manager.
* If you front your private space with Flex Gateway, Flex Gateway has its own separate timeout policies (Stream Idle Timeout, Upstream Idle Timeout, Response Timeout) configurable via Anypoint API Manager or Flex Gateway declarative configuration. These don't change the CloudHub 2.0 ingress timeouts above.

For CloudHub 2.0 timeout configuration, see https://docs.mulesoft.com/cloudhub-2/ps-config-advanced[Configure Private Space Advanced Settings] and https://docs.mulesoft.com/cloudhub-2/ch2-limits[Limits in CloudHub 2.0]. +
For Flex Gateway timeout policies, see https://docs.mulesoft.com/gateway/latest/flex-conn-timeout[Configuring Timeouts in Connected Mode].

== CloudHub Features Not Supported in CloudHub 2.0

The following features are not supported on CloudHub 2.0:

* TLS 1.0 and TLS 1.1 — CloudHub 2.0 supports TLS 1.2 and TLS 1.3 only.
* Custom notifications using the CloudHub Connector — use Email Connector or Anypoint Monitoring alerts instead.
* VPN between a CloudHub 1.0 VPC and a CloudHub 2.0 private space — use Transit Gateway or separate VPN connections instead.
* VPC peering — migrate to Transit Gateway or VPN before upgrading a VPC.
* Direct Connect — migrate to Transit Gateway or VPN before upgrading a VPC.
* Peering connections are not migrated when you upgrade a VPC. Delete them manually before or after the upgrade.

[discrete]
== Useful Migration Facts

The following details apply during migration:

* Default VPN HA — VPN connections are created with high availability by default.
* Transit Gateway is preserved when a private space is deleted — you can delete and recreate a private space without losing TGW attachments.
* Static IPs and AZ count — If your VPC is deployed across two AZs, it has two sets of inbound static IPs. When you upgrade, the private space inherits the same AZ count (2 AZs → 2 AZs). To use a different AZ count, create a new private space manually instead.
* Secure properties are write-only — You can change a secure property value but can't read it back after creation. When migrating, re-enter the values in CloudHub 2.0 settings.
* Application name uniqueness — In CloudHub, app names are unique per control plane. In CloudHub 2.0, app names are unique per private space.
* Ingress logs — CloudHub 2.0 provides self-service access to ingress traffic logs via Runtime Manager. Application logs integrate with Titanium (Anypoint Monitoring) for full visibility.
* Internal load balancer — CloudHub 2.0's internal ingress load balancer listens on HTTP (80) and HTTPS (443) only. Inbound protocols are limited to HTTP, HTTPS, and TCP (TCP only on newly created private spaces, not upgraded ones).
