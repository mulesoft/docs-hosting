Use this page to diagnose and resolve common issues encountered during CloudHub to CloudHub 2.0 migration.

.Traffic Switching Issues
[%collapsible]
====
[discrete]
== Traffic Switching Issues

=== 502 Bad Gateway During Traffic Switch

TLS protocol incompatibility. The DLB requires TLS 1.2 or higher as the upstream protocol when routing to CloudHub 2.0 applications. If configured with only TLS 1.1, traffic switching to CloudHub 2.0 fails with a 502 error. Additionally, incorrect ingress endpoint selection can cause 404 errors after resolving the TLS issue.

To troubleshoot this issue:

. In *Runtime Manager*, select *CloudHub* > *Load Balancers*.
. Select your DLB and review the *Upstream TLS* settings.
. Make sure that *TLS 1.2 or higher* is enabled (it can be added alongside TLS 1.1).
. In your CloudHub 2.0 application, go to the *Ingress* tab and select the correct DLB endpoint from the dropdown.
. Verify that the endpoint mapping matches your DLB vanity domain configuration.

For more information, see https://help.salesforce.com/s/articleView?id=005315578&type=1[KA 005315578].

=== Failed to Update Traffic Switching Percentage

Missing permissions, incorrect application configuration, or certificate migration issues can prevent the traffic switching percentage from being updated.

To troubleshoot this issue:

. Verify that the user has the *CloudHub Network Administrator* permission.
. Verify that both CloudHub 1.0 and CloudHub 2.0 applications are deployed and running.
. Verify that the CloudHub 2.0 application's HTTP Listener is listening on port 8081.
. Verify that Last-Mile Security is enabled only if your application has a TLS context.
. If migrating with a DLB, go to *Runtime Manager* > *Private Spaces* > your private space > *Domains & TLS* and verify that the DLB certificate was migrated. If it's missing, upload it and create a TLS context.

NOTE: The DLB requires a full chain (intermediate and root certificates). For the private space, split intermediate and root certificates into a single file and upload as *CA Path Certificate*.

For more information, see https://help.salesforce.com/s/articleView?id=005321445&type=1[KA 005321445].

.Certificate and TLS Issues
[%collapsible]
====
[discrete]
== Certificate and TLS Issues

=== Missing DLB Certificates Post-Upgrade

The VPC upgrade tool migrates DLB configurations on a *best-effort basis only*. Due to architectural differences between the DLB and CloudHub 2.0 ingress controller, automated certificate migration isn't guaranteed.

To troubleshoot this issue:

. In *Runtime Manager*, go to your private space > *Domains & TLS* tab.
. Manually upload your server certificates and private keys.
. Verify that all Subject Alternative Names (SANs) for vanity domains are correctly listed.
. Create TLS contexts for each vanity domain.

NOTE: Split intermediate and root certificates into a separate file and upload as the *CA Path Certificate*.

For more information, see https://help.salesforce.com/s/articleView?id=005237268&type=1[KA 005237268].

=== TLS Handshake Failure

Certificates aren't applied to the ingress load balancer, or incompatible TLS 1.1 ciphers are in use.

To troubleshoot this issue:

. Upload certificates to the ingress load balancer in the private space's *Domains & TLS* tab.
. Verify that no TLS 1.1-only ciphers are in use:
** `ECDHE-ECDSA-AES128-SHA1`
** `ECDHE-ECDSA-AES256-SHA1`
** `ECDHE-RSA-AES128-SHA1`
** `ECDHE-RSA-AES256-SHA1`
. If these ciphers are present, reissue certificates with TLS 1.2+ compatible ciphers.

[cols="1,2,2,1"]
|===
|Symptom |Likely Cause |Resolution |Reference

|CloudHub 2.0 application can't connect to CloudHub application
|DLB allowlist missing infrastructure CIDR ranges.
|Add the following CIDR ranges to the DLB allowlist: `100.64.0.0/16`, `100.66.0.0/16`, `100.67.0.0/16`, `100.68.0.0/16`.

|Incorrect private space firewall rules or missing internal network configuration.
|Add an ingress rule allowing traffic from the local private network. Verify domain configuration.

|Firewall rules not migrated correctly to the private space.
|Check firewall rules in the private space. Verify VPN and transit gateway routing tables.
|

|DNS not resolving
|DNS CNAME not updated to point to CloudHub 2.0 endpoints.
|Update the DNS CNAME to point to the ingress load balancer endpoint.
|

=== Oracle Stored Procedure Dropping Connections After 8 Minutes

After migrating to CloudHub 2.0, long-running stored procedure calls can terminate silently after approximately 8 minutes. An intermediate network component (load balancer, NAT gateway, or firewall) drops idle TCP connections without application-level error reporting.

To troubleshoot this issue:

* *Option 1:* Set JVM argument `oracle.net.keepAlive=true` in the Mule Runtime via Runtime Manager properties.
* *Option 2:* Use a Generic connection in the Database Connector with the keepAlive property in the JDBC URL:
+
----
jdbc:oracle:thin:@//host:port/service?oracle.net.keepAlive=true
----

For more information, see https://help.salesforce.com/s/articleView?id=005321536&type=1[KA 005321536].

.VPC Upgrade Issues
[%collapsible]
====
[discrete]
== VPC Upgrade Issues

[cols="1,2,2"]
|===
|Symptom |Likely Cause |Resolution

|Upgrade tooling isn't available on the Settings page
|Application isn't in an eligible VPC, or VPC hasn't been upgraded yet.
|Verify that the VPC meets xref:cloudhub::vpc-upgrade.adoc#understand-eligibility[eligibility requirements] and has been upgraded to a private space first.

|Upgrade fails with CIDR conflict
|The VPC CIDR block is smaller than /24 or doesn't have 100+ available IPs per subnet.
|Review CIDR allocation. If the block is too small, then create a new private space manually instead.

|DLB certificates missing after upgrade
|TLS 1.1 ciphers present in the original certificate, or transfer failure during best-effort migration.
|Re-upload certificates to the private space *Domains & TLS* tab. If they use TLS 1.1 ciphers, then reissue the certificates. See <<missing-dlb-certificates-post-upgrade>>.

|Upgrade tooling doesn't support default VPC
|Only named VPCs can be upgraded. The default VPC isn't eligible.
|Create a new private space manually. Deploy applications directly to the new private space.

|Private space doesn't appear after upgrade
|Upgrade is still in progress, or the upgrade failed silently.
|Wait up to 30 minutes. If the private space still doesn't appear, then check *Runtime Manager* > *Private Spaces* and contact MuleSoft Support.

|Can't delete VPC after upgrade
|Migration not marked complete, or environments still associated with the VPC.
|Mark the migration as complete for all applications in the VPC. Dissociate all environments. See https://help.salesforce.com/s/articleView?language=en_US&id=005115579&type=1[KA 005115579].
|===

For upgrade steps, see xref:ch2-migration-infrastructure.adoc#upgrade-a-vpc-to-a-private-space[Upgrade a VPC to a Private Space].

.Infrastructure Issues
[%collapsible]
====
[discrete]
== Infrastructure Issues

[cols="1,2,2,1"]
|===
|Symptom |Likely Cause |Resolution |Reference

|CIDR block conflict during private space creation
|CIDR block overlaps with existing on-premises or cloud networks.
|Choose a non-overlapping CIDR block. Review existing allocations before creating.
|xref:ch2-migration-infrastructure.adoc#create-a-new-private-space-manually[Create a New Private Space Manually]

|VPN tunnel not establishing to new private space
|Routing tables or security group configurations not updated for new private space.
|Verify routing tables. Confirm VPN configuration matches private space network settings.
|xref:ch2-migration-infrastructure.adoc#step-4-establish-network-connectivity[Establish Network Connectivity]

|Missing DLB certificates post-upgrade
|TLS 1.1 cipher incompatibility or transfer failure during upgrade.
|Re-upload certificates to private space. Validate supported ciphers. See https://help.salesforce.com/s/articleView?id=sf.000005237268&type=5[Missing DLB Certificates During CloudHub 1.0 to CloudHub 2.0 Migration].
|<<missing-dlb-certificates-post-upgrade>>

|Firewall rules not migrated correctly
|Ports other than 80, 443, and 30500–32500 are dropped during migration.
|Manually recreate dropped firewall rules in the private space.
|xref:ps-config-fw-rules.adoc[Configure Firewall Rules]

|Cannot upgrade default VPC
|Upgrade tooling doesn't support default VPC.
|Disable the default VPC configuration before proceeding with the upgrade.
|xref:ch2-migration-infrastructure.adoc#step-2-review-environment-association[Review Environment Association]

|Can't delete VPC after migration
|Migration not marked complete, or environment still associated.
|Mark upgrade complete in Runtime Manager. Verify that no environments are associated.
|https://help.salesforce.com/s/articleView?language=en_US&id=005115579&type=1[KA 005115579]

|Application doesn't start on CloudHub 2.0
|Incompatible Mule runtime version. CloudHub 2.0 requires Mule 4.3.x or later.
|Upgrade the application to Mule 4.4 or later and rebuild the JAR. Verify `minMuleVersion` in `mule-artifact.json`.
|xref:mule-runtime::updating-mule-4-versions.adoc[Updating Mule 4 Versions]

|Connection refused from on-premises systems
|Private space firewall rules don't allow egress to on-premises destinations, or transit gateway/VPN routing not configured.
|Add egress firewall rules for the on-premises CIDR range. Verify that the transit gateway attachment or VPN tunnel is active and that routing tables include the destination.
|xref:ps-config-fw-rules.adoc[Configure Firewall Rules]

|TLS handshake failure
|Certificates not uploaded to the private space TLS context, or TLS 1.1 ciphers in use.
|Upload certificates to the private space *Domains & TLS* tab. Verify that all certificates use TLS 1.2 or higher compatible ciphers.
|xref:ps-config-domains.adoc[Configure Domains]

|Application properties missing after migration
|Secure properties aren't carried over automatically. Copied properties require at least one edit to persist.
|Re-enter all secure property values in the CloudHub 2.0 application settings. Edit or add at least one property to persist all copied properties.
|xref:cloudhub::app-migration.adoc#application-properties[Application Properties]

|DNS not resolving for CloudHub 2.0 application
|DNS CNAME not updated to point to the CloudHub 2.0 ingress endpoint, or DNS negative caching after DLB restart.
|Update DNS CNAME to point to `[space-id].[region].cloudhub.io`. If DLB was recently restarted, wait 15 minutes for negative DNS cache to expire.
|xref:ch2-networking-guide.adoc[CloudHub 2.0 Networking Architecture]

|High latency after migration
|Replica size under-provisioned compared to original CloudHub worker size.
|Increase replica vCore size or replica count. Compare original worker sizing to current replica allocation using the vCore equivalency table.
|xref:ch2-architecture.adoc#cloudhub-2-replicas[CloudHub 2.0 Replicas]

|Scheduler not firing in CloudHub 2.0
|Scheduler behavior differs in a clustered environment. In CloudHub 2.0, only one replica executes the scheduler when clustering is enabled.
|Verify that scheduler configuration is compatible with CloudHub 2.0 clustering. Review timezone settings. See scheduler management docs for CloudHub 2.0-specific behavior.
|xref:ch2-manage-schedules.adoc[Manage Schedules]
|===

.Connectivity Diagnostics
[%collapsible]
====
[discrete]
== Connectivity Diagnostics

To diagnose connectivity issues between CloudHub platforms during migration, deploy the MuleSoft Network Tools application to your VPC or private space. The following tests are available:

* *Socket test:* Verify TCP connectivity between platforms (equivalent to a TCP handshake).
* *DNS test:* Confirm DNS resolution for DLB and ingress endpoints.
* *cURL test:* Validate HTTP/HTTPS endpoint accessibility end-to-end.
* *Certificate test:* Inspect TLS certificates presented by an endpoint.
* *Cipher test:* Identify which TLS ciphers a remote endpoint supports.

NOTE: In CloudHub 2.0 private spaces, *Ping* isn't supported due to security restrictions. Use TCP socket tests instead.

See https://help.salesforce.com/s/articleView?id=001115029&type=1[How To Use Network Tools Application For Connectivity Test From CloudHub VPC (KA 001115029)].
