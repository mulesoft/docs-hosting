[[create-a-new-private-space-manually]]
== Create a New Private Space Manually

// Source: Consolidated from ch-ch2-migration-configuration "Before You Begin" + "Create Your Private Space"
// Expanded with procedural steps per improvement plan Section 1.1 Step 2

Create a new private space when your VPC isn't eligible for the upgrade tool, or when you need both CloudHub and CloudHub 2.0 to coexist on the same network with independent CIDR blocks.

=== Prerequisites

Gather the following information from your existing CloudHub environment before creating a private space:

// Source: Reused from ch-ch2-migration-configuration "Before You Begin"

* CIDR block information
+
If you require both CloudHub and CloudHub 2.0 to exist at the same time on the same network, then use a new CIDR block for CloudHub 2.0.

* VPN connection information
* SSL certificates
* DNS server information
* Ingress firewall rules
* Mule application code

For complete requirements, see xref:ps-gather-setup-info.adoc#setup-info-private-space[Information Required to Set Up a Private Space].

=== Step 1: Define a CIDR Block

Allocate a CIDR block for the new private space:

* The CIDR block can't overlap with on-premises or other cloud networks.
* If CloudHub and CloudHub 2.0 must coexist on the same network, then choose a CIDR block that doesn't overlap with your existing VPC's CIDR range.
* Plan for adequate IP address space to accommodate all applications and future growth.

For CIDR block requirements, see xref:ps-gather-setup-info.adoc#cidr-block[CIDR Block].

=== Step 2: Create the Private Space

Create and configure your CloudHub 2.0 private space using one of these methods:

// Source: Reused from ch-ch2-migration-configuration "Create Your Private Space"

* https://anypoint.mulesoft.com/exchange/portals/anypoint-platform/f1e97bc6-315a-4490-82a7-23abe036327a.anypoint-platform/cloudhub-20-api/[CloudHub 2.0 API]
* Anypoint Runtime Manager — See xref:ps-create-configure.adoc[Create a Private Space via Runtime Manager].

=== Step 3: Configure Firewall Rules

All traffic to a private space is blocked by default until explicitly allowed by a firewall rule.

* Configure inbound firewall rules to allow traffic to your applications.
* Configure outbound (egress) firewall rules to allow applications to reach required destinations.
* Review xref:ps-config-fw-rules.adoc[Configure Firewall Rules for a Private Space] for detailed instructions.

=== Step 4: Establish Network Connectivity

Reestablish VPN tunnels or Transit Gateway (TGW) attachments to the new private space:

* Configure VPN or TGW connections to the new private space.
* Validate that routing tables have correct traffic flow.
* Test connectivity between the private space and on-premises or other cloud networks.
* Verify that DNS resolution works for both internal and external services.

=== Step 5: Configure TLS and DNS

* If you're using a DLB in CloudHub, configure custom TLS certificates in your private space.
+
// Source: Reused from ch-ch2-migration-configuration "Create Your Private Space"
+
* Upload SSL certificates to the private space's ingress load balancer.
* Update DNS records (CNAME) to point to the new private space load balancer endpoint.
* Configure custom vanity domains with your own TLS context if needed.

For TLS configuration, see xref:ps-config-domains.adoc[Configure Domains and TLS for a Private Space].

=== Step 6: Validate the Private Space

After creating the private space, confirm:

* The private space appears under *Runtime Manager* > *Private Spaces*.
* Firewall rules are correctly configured (inbound and outbound).
* VPN or TGW connections are stable.
* DNS resolution works for both internal and external services.
* TLS contexts are correctly applied.

[[upgrade-a-vpc-to-a-private-space]]
== Upgrade a VPC to a Private Space

// Source: Content from vpc-upgrade, summarized here with cross-references.
// Per implementation plan decision: vpc-upgrade remains standalone; this section provides
// context and links to the full procedure.

Use the in-product VPC upgrade tool to migrate your CloudHub VPC to a CloudHub 2.0 private space while retaining your existing infrastructure configuration.

// Source: Reused from vpc-upgrade intro

The tool provisions the infrastructure for a CloudHub 2.0 private space by cloning the existing configurations of your eligible CloudHub dedicated VPC, using the same CIDR block. Existing Transit Gateway (TGW) and VPN connections transfer seamlessly to the new CloudHub 2.0 private space.

The default CloudHub certificates are configured as part of the private space's default certificates. The DLB custom domains of the migrated VPC are created as part of the private space's custom TLS certificates.

=== Step 1: Complete the Eligibility Checklist

Before starting the upgrade, confirm that your VPC meets all eligibility requirements:

// Source: Reused from vpc-upgrade#understand-eligibility (summarized)

* VPC has at least 25% free space and 100+ available IP addresses per subnet.
* No legacy VPNs configured.
* No Direct Connect or VPC Peering (migrate to Transit Gateway or VPN first).
* No TLS 1.1 ciphers that can't be carried over (ECDHE-ECDSA-AES128-SHA1, ECDHE-ECDSA-AES256-SHA1, ECDHE-RSA-AES128-SHA1, ECDHE-RSA-AES256-SHA1).
* Default VPC configuration is disabled.

For the complete eligibility checklist, see xref:cloudhub::vpc-upgrade.adoc#understand-eligibility[Understand Eligibility].

=== Step 2: Review Environment Association

// Source: Reused from vpc-upgrade#understand-environment-association

During the upgrade, the environments associated with your VPC stay in sync with the environments associated with the upgraded CloudHub 2.0 private space to avoid configuration drift.

Key considerations:

* In CloudHub 2.0, an environment can be associated with multiple private spaces. In CloudHub, one environment can only be associated with one VPC in a given region.
* Bulk environment association for an upgraded private space can result in all environments in the same region getting associated with the underlying VPC. If those environments were previously associated with other CloudHub 1.0 VPCs, they get disassociated.

WARNING: The upgrade tooling doesn't support the upgrade of a default VPC. To proceed with the upgrade, disable the default VPC configuration.

For full details, see xref:cloudhub::vpc-upgrade.adoc#understand-environment-association[Understand Environment Association].

=== Step 3: Run the Upgrade

// Source: Reused from vpc-upgrade#upgrade-your-vpc-via-anypoint-platform

. From *Anypoint Platform*, select *Runtime Manager* > *Upgrade*.
. Click *Upgrade Now* in the *Upgrade Status* column for the VPC to upgrade.
+
The *Upgrade to CloudHub 2.0* review page displays the configurations currently available in your VPC and the configurations created during the upgrade.
. Click *Next* to continue.
. Provide a name for the new private space.
+
Optionally, specify xref:ps-gather-setup-info.adoc#cidr-block[reserved CIDRs] to connect to your new private space.
. Click *Create* to create the new private space.
+
The upgrade process takes about 15 to 30 minutes.

The tool validates:

* CIDR block compatibility
* Firewall rules migration
* Associated DLB configurations

Existing CloudHub applications continue running uninterrupted during the upgrade.

NOTE: If you create a VPN to provision your CloudHub VPC, wait until the newly created VPN status shows as available before migrating your VPC to a CloudHub 2.0 private space.

As soon as the upgrade process starts, the upgraded VPC is locked for any further updates.

To revert to your VPC at any time, click *Cancel Upgrade*. The system deletes the newly created private space and unlocks your VPC.

After the private space is provisioned, the *Cancel Upgrade* button no longer appears. To roll back, delete the private space.

=== Step 4: Validate the Private Space Upgrade

After the upgrade completes:

* Confirm that the private space appears under *Runtime Manager* > *Private Spaces*.
* Verify that xref:ps-config-app-level-egress.adoc[egress rules] are applied correctly.
* Verify that xref:ps-config-fw-rules.adoc[firewall rules] are correctly copied and that outgoing firewall rules allow necessary destinations while restricting other destinations.
* Verify that Transit Gateway and VPN connections are stable.
* Verify that DNS resolution works for both internal and external services.
* Check that DLB certificates transferred successfully. If certificates are missing or your apps require specific TLS configurations, then manually add TLS contexts using the *Domains & TLS* tab.

// Source: Validation steps per improvement plan + vpc-upgrade DLB certificate note

IMPORTANT: The VPC upgrade tool migrates DLB certificates on a best-effort basis only. Verify that all certificates are present after the upgrade.

=== Troubleshoot Common Upgrade Failures

// Source: Improvement plan Step 2, item 5 — Troubleshooting common upgrade failures

[cols="1,2,2"]
|===
|Symptom |Likely Cause |Resolution

|Upgrade tooling isn't available on the Settings page
|Application isn't in an eligible VPC, or VPC hasn't been upgraded yet.
|Verify that the VPC meets xref:cloudhub::vpc-upgrade.adoc#understand-eligibility[eligibility requirements] and has been upgraded to a private space first.

|Upgrade fails with CIDR conflict
|The VPC CIDR block is smaller than /24 or doesn't have 100+ available IPs per subnet.
|Review CIDR allocation. If the block is too small, then create a new private space manually instead.

|DLB certificates missing after upgrade
|TLS 1.1 ciphers present in the original certificate, or transfer failure during best-effort migration.
|Re-upload certificates to the private space *Domains & TLS* tab. If they use TLS 1.1 ciphers, then reissue the certificates.

|Upgrade tooling doesn't support default VPC
|Only named VPCs can be upgraded. The default VPC isn't eligible.
|Create a new private space manually. Deploy applications directly to the new private space.

|Private space doesn't appear after upgrade
|Upgrade is still in progress, or the upgrade failed silently.
|Wait up to 30 minutes. If the private space still doesn't appear, then check *Runtime Manager* > *Private Spaces* and contact MuleSoft Support.

|Can't delete VPC after upgrade
|Migration not marked complete, or environments still associated with the VPC.
|Mark the migration as complete for all applications in the VPC. Dissociate all environments. See https://help.salesforce.com/s/articleView?language=en_US&id=005115579&type=1[KA 005115579].
|===

For additional troubleshooting, see xref:ch2-migration-troubleshoot.adoc[Troubleshoot Migration Issues].

== Enable Cross-Platform Communication

// Source: Reused from vpc-upgrade "Enable CloudHub 2.0 Apps to Communicate with CloudHub Apps via DLB"
// Expanded with Section 2, Deliverable B.1 — CH2→CH1 detailed configuration steps and B.5 diagram

During a phased migration, applications on CloudHub 2.0 and CloudHub 1.0 must communicate across platforms. This section covers the connectivity configuration required for cross-platform communication.

=== CloudHub 2.0 to CloudHub 1.0 (via DLB)

Because CloudHub 2.0 uses a separate infrastructure CIDR pool, the DLB doesn't allow traffic from CloudHub 2.0 apps by default.

==== Step 1: Add Infrastructure CIDR Ranges to the DLB Allowlist

Add the following CloudHub 2.0 infrastructure CIDR ranges to your DLB allowlist:

* `100.64.0.0/16`
* `100.66.0.0/16`
* `100.67.0.0/16`
* `100.68.0.0/16`

To update the DLB allowlist:

. In *Runtime Manager*, navigate to *CloudHub* > *Load Balancers*.
. Select your DLB.
. In the *Whitelists* tab, add each CIDR range.
. Save the configuration.

For more information about CloudHub 2.0 infrastructure CIDR ranges, see xref:ps-gather-setup-info.adoc#infra-cidr-pool[Infrastructure CIDR Pool].

==== Step 2: Configure DNS Resolution

Your CloudHub 2.0 application must resolve the CloudHub 1.0 application's DLB endpoint:

* If using a DLB vanity domain: Point your CloudHub 2.0 app to the vanity domain URL (for example, `api.example.com`). DNS resolves to the DLB, which routes to the CloudHub 1.0 worker.
* If using the default `cloudhub.io` endpoint: Use the standard endpoint format `<app-name>.<region>.cloudhub.io`.

==== Step 3: Verify DLB TLS Configuration

The DLB must support TLS 1.2+ for upstream connections from CloudHub 2.0:

. In *Runtime Manager*, navigate to *CloudHub* > *Load Balancers*.
. Select your DLB and review the *Upstream TLS* settings.
. Confirm that *TLS 1.2 or higher* is enabled as an upstream protocol.

NOTE: TLS 1.2 can be added alongside TLS 1.1 without disrupting existing connections. See https://help.salesforce.com/s/articleView?id=005315578&type=1[502 Bad Gateway Error When Switching Traffic (KA 005315578)].

==== Step 4: Configure Egress Rules in the Private Space

Confirm that the CloudHub 2.0 private space allows outbound traffic to the DLB endpoints:

* If using a VPN or Transit Gateway connection, then verify that routing tables include the DLB endpoint.
* If accessing via public endpoints, then configure application-level egress rules. See xref:ps-config-app-level-egress.adoc[Configure Application-Level Egress].

=== CloudHub 1.0 to CloudHub 2.0

// NOTE: This scenario needs engineering verification. The steps below are based on
// available documentation, but the exact routing path (direct vs. public internet vs. TGW)
// has not been confirmed by engineering.

For a CloudHub 1.0 application to call a CloudHub 2.0 application:

. *DNS resolution:* Configure the CloudHub 1.0 app to point to the CloudHub 2.0 application's ingress endpoint (the public URL assigned during CloudHub 2.0 deployment).
. *Firewall rules:* In the CloudHub 2.0 private space, add ingress firewall rules to allow traffic from the CloudHub 1.0 VPC CIDR range.
. *TLS:* Confirm that the CloudHub 2.0 application has a valid TLS context configured if calling over HTTPS.

NOTE: Verify with your network team whether traffic between the CloudHub VPC and CloudHub 2.0 private space routes through the public internet or can use internal routing via VPN or Transit Gateway.

=== CloudHub 2.0 to CloudHub 2.0

// Source: Section 2, Deliverable B.3 — CH2→CH2 connectivity patterns
// Based on: docs.mulesoft.com/cloudhub-2/ch2-config-endpoints-paths
// "Send Application-to-Application Requests within a Private Space"

==== Same Private Space

Applications in the same private space can communicate using several endpoint types:

[cols="1,2,1"]
|===
|Endpoint Type |Format |Notes

|Cluster-local DNS (same environment)
|`http://<app-name>:8081/<path>`
|Fastest. Traffic doesn't leave the cluster. Not highly available during disaster recovery — if an app migrates to a new cluster, this endpoint becomes unreachable. Deploy multiple replicas for availability during node upgrades.

|Full cluster-local DNS
|`<app-name>.<environment-id>.svc.cluster.local:8081`
|Same as above with explicit namespace. Only works within the same environment.

|Internal DNS
|`<app-name>.internal-<id>.<region>.cloudhub.io`
|Traffic stays within the private space network. Remains reachable during disaster recovery because it routes through the ingress load balancer.

|Default public DNS
|`<app-name>.<id>.<region>.cloudhub.io`
|Routes through the public ingress. Unnecessary overhead for same-space communication but always works.
|===

IMPORTANT: Cluster-local DNS endpoints (`svc.cluster.local`) can't send traffic between applications in different namespaces (environments). Use internal or public DNS for cross-environment communication.

TIP: For production workloads, use the *internal DNS* endpoint rather than cluster-local. It provides high availability during disaster recovery because traffic traverses the ingress load balancer, which can redirect to a new cluster if needed.

==== Different Private Spaces

Applications in different private spaces can't use cluster-local or internal DNS endpoints. Use one of the following:

* *Public endpoint:* Use the target app's public DNS name or custom domain. Confirm that the target private space's firewall rules allow inbound traffic.
* *Transit Gateway:* If both private spaces are attached to the same transit gateway, traffic can route through the TGW. Configure routes on both sides.

=== Transit Gateway Configuration During Migration

// Source: Section 2, Deliverable B.4 — Transit Gateway hybrid setup
// Based on: docs.mulesoft.com/cloudhub-2/ps-create-configure-tgw

If your CloudHub 1.0 VPC uses a Transit Gateway (TGW) for on-premises connectivity, then you need both the existing CloudHub VPC TGW attachment and a new CloudHub 2.0 private space TGW attachment during migration.

==== VPC Upgrade Path

If using the VPC upgrade tool, existing TGW connections transfer to the new CloudHub 2.0 private space automatically. No additional TGW configuration is needed.

==== Manual Private Space Path

If creating a new private space manually, then attach it to your existing transit gateway:

. In *Runtime Manager*, navigate to *Private Spaces* > your space > *Network* tab.
. In the *Connections* section, click *Create Connection* > *Transit Gateway*.
. Select your existing transit gateway or add a new one.
. Configure static routes matching your on-premises VPC CIDR ranges.
. Create the AWS resource share (if new TGW) and accept the attachment in AWS.
. Update your AWS transit gateway route tables to include the new private space CIDR.

==== Hybrid Routing During Migration

During phased migration with both CloudHub and CloudHub 2.0 attached to the same TGW:

* On-premises systems reach CloudHub apps via VPC routes through the TGW.
* On-premises systems reach CloudHub 2.0 apps via private space routes through the TGW.
* Confirm that route tables on the TGW don't have CIDR conflicts between the CloudHub VPC and CloudHub 2.0 private space.

==== Validate TGW Connectivity

After attaching the transit gateway, test connectivity using the Network Tools application:

. Deploy Network Tools to the new private space.
. Use the *Socket* test to verify TCP connectivity to on-premises hosts via the TGW.
. Use the *Traceroute* test to confirm the traffic path traverses the TGW.

For full TGW configuration steps, see https://docs.mulesoft.com/cloudhub-2/ps-create-configure-tgw[Creating Transit Gateway Attachments].

=== Validate Connectivity

After configuring cross-platform communication, validate connectivity using the MuleSoft Network Tools application:

. Deploy the Network Tools app to your VPC or private space.

. Use the *cURL* test to validate HTTP/HTTPS endpoint accessibility.
. Use the *DNS* test to confirm DNS resolution for DLB and ingress endpoints.

== Plan for Static IP Changes

// Source: Section 3, Deliverable B — Static IP provisioning guide
// Based on: _partials/ch1-ch2-static-ips.adoc, cloudhub-networking-guide, ps-about

Static IP allocation differs between CloudHub and CloudHub 2.0:

[cols="1,1,1"]
|===
|Aspect |CloudHub |CloudHub 2.0

|Scope
|Per-application. Each app can have its own outbound static IP.
|Per-private-space. All apps in a private space share the same set of outbound static IPs.

|Inbound static IPs
|Available only through a DLB. All apps behind the same DLB share inbound static IPs.
|Provided at the private space level. All apps in the same private space share inbound static IPs.

|Unique IPs per app
|Enable *Static IPs* in application settings to get per-app outbound IPs.
|Not available within a single private space. To have unique static IPs per application, deploy to a different private space.
|===

=== Impact on Backend System Allowlists

If backend systems (databases, SaaS APIs, on-premises services) have firewall rules that allow traffic only from specific CloudHub 1.0 application static IPs, you must update those rules to allow the new private space outbound IPs.

*Planning checklist:*

. Inventory all backend systems that allowlist traffic by source IP.
. For each system, record the current CloudHub 1.0 static IPs in use.
. After creating your CloudHub 2.0 private space, locate the private space's outbound NAT IPs:
** In *Runtime Manager*, navigate to *Private Spaces* > your space > *Network* tab.
. Update backend allowlists to include the new private space outbound IPs.
. During migration, keep *both* the old CloudHub IPs and new CloudHub 2.0 IPs in backend allowlists until decommissioning is complete.

=== Considerations

* If a backend system uses per-app source IP to identify *which* application is calling (rather than just for access control), this model no longer works in CloudHub 2.0 since all apps share outbound IPs. Use mTLS client certificates or API keys for application-level identification instead.
* Static IP allocation in CloudHub 1.0 is limited to twice the number of production vCores in your subscription. CloudHub 2.0 doesn't have this per-app limit — IPs are assigned per private space automatically.

== Maintain Business Continuity During Migration

// Source: Reused from vpc-upgrade "Next Steps After VPC Upgrade"

During the migration, continue deploying and managing applications in your VPC to maintain business continuity.

Key constraints after upgrade:

* Your CloudHub dedicated VPC is locked for any changes to the infrastructure, including environment or business group associations, network connections, and internal DNS.
* Make any required infrastructure changes to the newly created private space.
* The upgrade process applies CloudHub 2.0 configuration changes to the CloudHub VPC.
* If your CloudHub VPC doesn't have any network connections and you create new ones in your new CloudHub 2.0 private space after the upgrade, these new connections aren't reflected in your CloudHub VPC.

To avoid configuration drift, apply firewall rule changes in both the VPC and the private space throughout the migration.

WARNING: VPC firewall rules that have ports other than `80`, `443`, and `30500` to `32500` drop during the migration.

== Troubleshoot Common Infrastructure Issues

[cols="1,2,2"]
|===
|Issue |Likely Cause |Resolution

|CIDR block conflict during private space creation
|CIDR block overlaps with existing on-premises or cloud networks.

|Ports other than 80, 443, and 30500–32500 are dropped during migration.
|Manually recreate dropped firewall rules in the private space.

|Cannot upgrade default VPC
|Upgrade tooling doesn't support default VPC.
|Disable the default VPC configuration before proceeding with the upgrade.
|===
