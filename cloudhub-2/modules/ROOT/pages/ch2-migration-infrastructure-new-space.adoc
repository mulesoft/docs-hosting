= Create a New Private Space Manually
ifndef::env-site,env-github[]
include::_attributes.adoc[]
endif::[]

Create a new private space when your VPC isn't eligible for the upgrade tool, or when you need both CloudHub and CloudHub 2.0 to coexist on the same network with independent CIDR blocks.

== Prerequisites

Gather the following information from your existing CloudHub environment before creating a private space:

* CIDR block information
+
If CloudHub and CloudHub 2.0 must coexist on the same network, use a new CIDR block for CloudHub 2.0.

* VPN connection information
* SSL certificates
* DNS server information
* Ingress firewall rules
* Mule application code

For complete requirements, see xref:ps-gather-setup-info.adoc#setup-info-private-space[Information Required to Set Up a Private Space].

== Step 1: Define a CIDR Block

Allocate a CIDR block that fits your workloads and doesn't conflict with other networks:

* The CIDR block must be between /16 and /24, and you can't change it after the private space is created. A /22 block is recommended for most workloads.
* The CIDR block can't overlap with on-premises or other cloud networks, or with another private space.
* The CIDR block can't use these unusable ranges: `100.64.0.0/10`, `198.19.0.0/16`, `224.0.0.0/4`, `169.254.0.0/16`, `127.0.0.0/8`, `172.17.0.0/16`, `0.0.0.0/8`.
* If CloudHub and CloudHub 2.0 must coexist on the same network, choose a CIDR block that doesn't overlap with your existing VPC's CIDR range.
* Plan for adequate IP address space to accommodate all applications and future growth. Undersizing the CIDR block can cause replicas to fail with "replicas are unschedulable due to insufficient available IP addresses" — see the sizing tiers in xref:ps-gather-setup-info.adoc#cidr-block[CIDR Block].

For CIDR block requirements, see xref:ps-gather-setup-info.adoc#cidr-block[CIDR Block].

== Step 2: Create the Private Space

Create and configure your CloudHub 2.0 private space using one of these methods:

* https://anypoint.mulesoft.com/exchange/portals/anypoint-platform/f1e97bc6-315a-4490-82a7-23abe036327a.anypoint-platform/cloudhub-20-api/[CloudHub 2.0 API]
* Anypoint Runtime Manager — See xref:ps-create-configure.adoc[Create a Private Space via Runtime Manager].

== Step 3: Configure Firewall Rules

A new private space has default inbound firewall rules that allow HTTPS (443) and HTTP (80) traffic from `0.0.0.0/0`, and a default outbound rule that allows all egress traffic. You can configure up to 300 firewall rules per direction (inbound and outbound).

* Configure additional inbound firewall rules if you need to allow traffic from other ports, or to restrict inbound traffic to specific CIDR ranges.
* Configure outbound (egress) firewall rules if you want to restrict egress to specific destinations instead of relying on the default allow-all rule.
* Review xref:ps-config-fw-rules.adoc[Configure Firewall Rules for a Private Space] for detailed instructions.

== Step 4: Establish Network Connectivity

Reestablish VPN tunnels or Transit Gateway (TGW) attachments to the new private space:

* Configure VPN or TGW connections to the new private space. Each VPN connection requires a single static public remote IP address and a unique /30 CIDR for the tunnel interface. Static routing requires a pre-shared key (PSK) and IPsec Dead Peer Detection (DPD); dynamic (BGP) routing requires perfect forward secrecy (PFS) and a local ASN in the range 64512–65534. A private space allows a maximum of 95 route table entries across all VPN and TGW connections. See xref:ps-gather-setup-info.adoc#vpn-requirements[VPN Requirements] for full details.
* If you use internal DNS servers, confirm that every DNS server returns identical records for the same query — inconsistent records cause intermittent `UnknownHostException` errors. You can't forward certain domains (including `cloudhub.io`, `mulesoft.com`, `anypointdns.net`, and `amazonaws.com`) to an internal DNS server, DNS server IP addresses can't fall in the unusable CIDR ranges, and the internal DNS domain list is limited to 255 characters total. See xref:ps-gather-setup-info.adoc#internal-dns-server[Internal DNS Servers].
* Verify that routing tables route traffic correctly.
* Test connectivity between the private space and on-premises or other cloud networks.

== Step 5: Configure TLS

Configure custom TLS certificates and vanity domains so the private space's ingress load balancer can serve your applications.

* If you're using a DLB in CloudHub, configure custom TLS certificates in your private space.
+
* Upload SSL certificates to the private space's ingress load balancer.
* Configure custom vanity domains with your own TLS context if needed. For TLS configuration, see xref:ps-config-domains.adoc[Configure Domains and TLS for a Private Space].
+
NOTE: Update DNS records during application migration, not during infrastructure setup. Until apps are migrated, keep DNS pointing to your CloudHub load balancer.

== Step 6: Validate the Private Space

Confirm that the private space is created and configured correctly:

* The private space appears under *Runtime Manager* > *Private Spaces*.
* Firewall rules are correctly configured (inbound and outbound).
* VPN or TGW connections are stable.
* TLS contexts are correctly applied.
