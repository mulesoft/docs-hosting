= Deploying Mule Apps to Hybrid Standalone Instances

Deploy your Mule applications to hybrid standalone instances for on-premises execution with centralized cloud-based management, enabling secure integration within your infrastructure while maintaining operational visibility and control.

== Overview

Deploy Mule applications to your hybrid standalone infrastructure through Runtime Manager's centralized console, which provides comprehensive deployment management including target selection, configuration management, and operational monitoring.

Key deployment capabilities include:

* Multi-target deployment: servers, server groups, and clusters
* Application source flexibility: Exchange, local files, and environment promotion
* Configuration management: properties, logging, and monitoring settings
* Real-time deployment tracking and status monitoring
* Post-deployment management and update capabilities

== Deployment Targets

Select deployment targets based on your application's availability requirements, load distribution needs, and infrastructure architecture.

=== Individual Servers

Deploy to specific server instances for development, testing, or applications requiring dedicated resources:

* **Use Case**: Development environments, specialized applications, resource-intensive workloads
* **Benefits**: Dedicated resources, simplified troubleshooting, isolation from other applications
* **Considerations**: Single point of failure, manual scaling requirements

=== Server Groups

Deploy to multiple servers simultaneously for load distribution and horizontal scaling:

* **Use Case**: Load balancing, horizontal scaling, shared resource pools
* **Benefits**: Automatic load distribution, simplified management, coordinated deployments
* **Considerations**: Shared resources, potential resource contention between applications

=== Clusters

Deploy to high-availability clusters for mission-critical applications requiring fault tolerance:

* **Use Case**: Production applications, high-availability requirements, stateful applications
* **Benefits**: Automatic failover, shared memory, coordinated state management
* **Considerations**: Network overhead, configuration complexity, resource sharing

=== Deployment Methods

Choose from multiple deployment approaches based on your development workflow and integration requirements:

* **Runtime Manager Console** +
Web-based deployment through Anypoint Platform with visual deployment management
* **Runtime Manager API** +
Programmatic deployment for CI/CD pipelines and automated workflows
* **Maven Plugin** +
Integration with build processes for developer-centric deployment workflows

[IMPORTANT]
When you use Runtime Manager to manage a server, you cannot use other deployment methods or tools to manage that server. This ensures consistent state management and prevents configuration conflicts.

== Prerequisites

Ensure your hybrid standalone environment meets the deployment requirements before initiating application deployment.

=== Infrastructure Requirements

Complete the following infrastructure setup:

. **Mule Runtime Installation** +
xref:mule-runtime::runtime-installation-task.adoc[Download and install Mule] on target servers with appropriate Java version compatibility
. **Server Registration** +
xref:servers-create.adoc[Add servers to Runtime Manager] for centralized management and deployment capabilities
. **Network Configuration** +
Ensure servers have connectivity to Anypoint Platform for management communication

=== Environment Promotion Requirements

When promoting applications across environments (sandbox to production), verify these requirements:

* **Access Permissions** +
Valid permissions on both source and target environments for deployment operations
* **Version Compatibility** +
Identical or compatible Mule runtime versions across environments to prevent deployment failures
* **Target Architecture** +
Matching deployment target types (server, server group, cluster) between source and destination
* **Java Version Consistency** +
All servers in clusters must use the same Java version that matches application requirements

[NOTE]
You can verify Java version compatibility by checking server details in *Runtime Manager* > *Servers* before deployment.

=== Application Compatibility

Verify your application meets these deployment criteria:

* Application built for target Mule runtime version
* All dependencies available in target environment
* Configuration properties aligned with target environment requirements
* Resource requirements compatible with target server capacity



== Deploy Applications Through Runtime Manager

Deploy Mule applications to your hybrid standalone infrastructure using Runtime Manager's web console for comprehensive deployment management and monitoring.

=== Access the Deployment Interface

. Sign in to Anypoint Platform
. Navigate to *Runtime Manager*
. In the *Applications* page, click *Deploy application*

=== Configure Application Identity

**Application Name**

Provide a unique application name that identifies your deployment across environments:

* **Naming Rules**: 3-42 alphanumeric characters (a-z, A-Z, 0-9) and dashes (-) only
* **Uniqueness**: Must be unique within the target environment (Runtime Manager validates automatically)
* **Immutability**: Application names cannot be changed after deployment

[IMPORTANT]
Choose meaningful application names that reflect functionality or environment (e.g., `customer-api-prod`, `inventory-sync-dev`) for easier identification in operational dashboards.

**Deployment Target Selection**

Select your deployment target based on application requirements:

* Target must be in *Running* status to accept deployments
* Available options depend on your configured infrastructure (servers, server groups, clusters)
* Target selection determines available Mule runtime version for deployment

=== Application Source Configuration

Choose your application source based on development workflow and artifact management practices:

**Exchange Integration**

Deploy applications directly from Anypoint Exchange for centralized artifact management:

. Click *Choose file* > *Import file from Exchange*
. Select *Application* as the asset type
. Search for your application by name
. Select the target application and choose the desired version
. Click *Select* to confirm

Benefits: Version control, dependency management, organizational sharing

**Local File Upload**

Deploy applications from local development builds:

. Click *Choose file* > *Upload file*
. Browse and select your application JAR file
. Click *Open* to upload

Best for: Development testing, custom builds, hotfixes

**Environment Promotion**

Promote applications from non-production environments to maintain consistency:

. Click *Get from sandbox* (available when non-production environments exist)
. Select the source environment (e.g., Sandbox, QA)
. Search and select the application to promote
. Click *Apply* to inherit configuration

[NOTE]
Only applications deployed to hybrid standalone infrastructure can be promoted to other hybrid deployments. CloudHub applications require separate CloudHub-to-CloudHub promotion.

=== Deployment Configuration

Configure application settings through specialized configuration tabs before initiating deployment:

.The arrow shows the configuration tabs on the *Deploy Application* page.
image::rtm-deploy-to-own-servers.png[Configuration tabs on the Deploy Application page]

**Deployment Target Configuration**

Verify runtime compatibility between your application and target infrastructure:

* **Runtime Version**: Target selection automatically determines available Mule version
* **Compatibility Check**: Ensure this matches your application's development runtime version
* **Version Mismatch**: Incompatible versions cause deployment failures

**Insight Analytics Configuration**

Configure application analytics and monitoring metadata:

* **Business Events**: Enable tracking for business transaction monitoring
* **Custom Events**: Configure application-specific monitoring points
* **Performance Analysis**: Enable detailed transaction flow analysis

For comprehensive analytics configuration, see xref:insight.adoc[Insight].

**Application Properties Configuration**

Define runtime properties that control application behavior:

* **Environment Variables**: Configure environment-specific settings (endpoints, credentials, timeouts)
* **Property Inheritance**: Promoted applications retain original properties (editable before deployment)
* **Security Considerations**: Use secure property management for sensitive configuration data

Property Management Resources:
* xref:hybrid-manage-props.adoc[Manage Properties for Applications On-Premises]
* xref:secure-application-properties.adoc[Safely Hide Application Properties]

**Logging Configuration**

Set application-specific logging levels for operational visibility:

* **Available Levels**: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`
* **Runtime Override**: Logging configuration overrides application defaults
* **Alternative Configuration**: Modify `log4j2.xml` for advanced logging scenarios

Advanced Logging Resources:
* xref:mule-runtime::logging-in-mule.adoc#configuring-custom-logging-settings[Configuring Custom Logging Settings]
* https://logging.apache.org/log4j/2.x/manual/configuration.html[Apache Logging Services]

=== Post-Deployment Configuration Access

Additional configuration tabs become available after successful deployment:

* **Flow Monitoring** +
Enable individual flow performance tracking and analysis
* **Alerts History** +
Access historical alert data and notification patterns

=== Execute Deployment

. Click *Deploy Application* to initiate the deployment process
. Monitor deployment status in the Applications dashboard
. Verify successful deployment through application status indicators

The new application appears in the deployed applications list with a status indicator showing deployment progress and final state.

== Update Deployed Applications

Perform application updates through Runtime Manager to deploy new versions or apply configuration changes with minimal service disruption.

=== Application Version Updates

Update application artifacts while preserving existing configuration:

. Navigate to *Applications* page and select your deployed application
. Click *Choose File* to access update options
. Select new application version through the same source options:
   * Exchange version update
   * Local file upload
   * Environment promotion
. Review configuration changes if needed
. Click *Deploy Application* to apply updates

**Update Considerations:**

* **Downtime**: Brief service interruption occurs during application restart
* **Configuration Preservation**: Application properties and settings are retained
* **Version Rollback**: Keep previous versions available for quick rollback if needed
* **Testing**: Validate updates in non-production environments before production deployment

=== Configuration Updates

Modify application properties and settings without changing the application artifact:

. Select the deployed application from the Applications list
. Access configuration tabs (Properties, Logging, Insight)
. Make necessary configuration changes
. Apply changes to trigger configuration reload

== Troubleshooting Deployment Issues

Resolve deployment failures through systematic troubleshooting of common issues and error patterns.

=== Deployment Status Monitoring

Monitor deployment progress through application status indicators:

* **Deploying**: Application upload and installation in progress
* **Started**: Application successfully deployed and running
* **Failed**: Deployment encountered errors requiring attention
* **Stopped**: Application deployed but not currently running

=== Common Deployment Failures

**Runtime Version Mismatch**

* **Symptom**: Deployment fails with compatibility errors
* **Resolution**: Verify application and target runtime versions match
* **Prevention**: Use consistent runtime versions across development and deployment environments

**Resource Constraints**

* **Symptom**: Deployment timeout or memory errors
* **Resolution**: Check server resource availability and application requirements
* **Prevention**: Monitor server capacity and plan resource allocation

**Configuration Errors**

* **Symptom**: Application starts but fails during initialization
* **Resolution**: Review application logs for configuration issues
* **Prevention**: Validate properties and connectivity before deployment

=== Error Investigation

. **Check Application Status** +
Review status indicator and error messages in the Applications dashboard
. **Examine Deployment Logs** +
Access detailed error information through the application's log view
. **Verify Prerequisites** +
Confirm all deployment prerequisites are met (runtime version, connectivity, permissions)
. **Test Configuration** +
Validate application properties and external system connectivity
. **Retry Deployment** +
Correct identified issues and redeploy the application
